La formule magique — configuration.yaml
sensor:          # charge TOUS les .yaml dans sensors/ — fusionne en liste
  !include_dir_merge_list sensors/

template:         # idem pour les templates Jinja2
  !include_dir_merge_list templates/

utility_meter:     # chaque fichier doit retourner un DICT (pas une liste)
  !include_dir_merge_named utility_meter/

automation: !include automations.yaml    # fichier centralisé unique

!include_dir_merge_list fusionne tous les fichiers du dossier en une seule liste — parfait pour sensor: et template: qui acceptent plusieurs entités par fichier.
!include_dir_merge_named est obligatoire pour utility_meter: dont chaque compteur est une clé nommée (dict), pas un item de liste.

02 — Conventions

Descendre en enfer.

Les règles que chaque fichier YAML doit respecter. Sans exception.

1 — Numérotation officielle des pôles

5 pôles, préfixés P0 à P4. Chaque fichier YAML appartient à un seul pôle — jamais deux pôles dans le même fichier.

P0ENERGIE
P1CLIM
P2PRISES
P3ECLAIRAGE
P4PRESENCE
⊡
1 fonction = 1 fichier, par pôle

Chaque fichier YAML ne fait qu'une seule chose : mesurer, compter, calculer, ou afficher. On ne mélange jamais les pôles dans un même fichier. Une prise connectée ne cohabite pas avec un radiateur. L'approche monolithique est interdite.

2 — Numérotation officielle des pièces

Index fixe de 1 à 9 pour chaque pièce. Cet index précède le nom dans tous les titres secondaires de chaque fichier YAML, quel que soit le pôle.

1.ENTREE
2.CELLIER
3.TOILETTE
4.SALON
5.CUISINE
6.COULOIR
7.BUREAU
8.SDB
9.CHAMBRE

Exemple : la boite ┌ 4. SALON ┐ dans un fichier P1 signifie "ce bloc appartient au pôle Chauffage, pièce SALON (index 4)". La numérotation garantit l'ordre et l'unicité dans tout le projet.

3 — Abréviations officielles

Toutes les abréviations utilisées dans les noms de fichiers et les unique_id. Hors de cette liste = interdit.

Types de fichiers / entités

UMUtility Meter — compteur à remise à zéro par cycle
TPLTemplate — entité calculée, aucun hardware
AVGAverage — moyenne de puissance en W
kWhkilowatt-heure — unité d'énergie finale
CMDCommand Line — sensor via shell/script bash
Cycles / Divers
AMHQAnnuel / Mensuel / Hebdomadaire / Quotidien

4 — Convention de nommage : la chaîne de suffixes

Le suffixe du unique_id documente la dernière transformation subie. Chaque étape ajoute sa marque dans le nom.

source brute
{slug}_energy
Natif HA — Z2M / Hue / Shelly
→
Utility Meter
{slug}_{cycle}_um
Remis à zéro par cycle A/M/H/Q
→
Template (2 variantes)
{slug}_{cycle}_um_kwh_tpl
Relais kWh — exprime en énergie finale
{zone}_{cycle}_um_avg_tpl
Moyenne W — puissance moyenne sur le cycle
Règle absolue

Tout sensor sorti d'un Utility Meter finit par _um. Si ce sensor passe dans un template pour exprimer du kWh, il finit par _um_kwh_tpl. Si c'est pour une moyenne W : _um_avg_tpl.

Règle d'agrégation

Si un fichier _kwh_tpl existe déjà et que tu y ajoutes un nouveau sensor du même type, ce sensor porte aussi le suffixe _kwh_tpl — même logique, même fichier, même suffixe.

5 — Bordures ASCII

Chaque fichier YAML commence par une boîte ASCII. Deux niveaux : titre principal du fichier, titre secondaire par pièce.

Titre principal — coins arrondis

Caractères : ╭─╮ / ╰─╯
Largeur : 78 caractères
Texte : MAJUSCULES
Si le texte dépasse 74 car. : élargir la boîte (76, 80+).
Ne jamais supprimer les références techniques du titre.

Titre secondaire — coins carrés

Caractères : ┌─┐ / └─┘
Largeur : 37 caractères
Texte : MAJUSCULES, numérotation officielle 1-9
Un titre secondaire par pièce dans le fichier.
 

# titre principal - coins arrondis - 78 car. [exemple a 60 car.] # ╭──────────────────────────────────────────────────────────╮ # │ POLE 1 - UTILITY METER AMHQ : CHAUFFAGE CLIM │ # ╰──────────────────────────────────────────────────────────╯ # titre secondaire - coins carres - 37 car. # ┌───────────────────────────────────┐ # │ 4. SALON │ # └───────────────────────────────────┘

6 — Les 5 headers obligatoires

Juste sous la boîte ASCII principale, dans cet ordre exact. Toujours les 5 — même si une section est vide.

📝
## 📝 DESCRIPTION :
Ce que fait le fichier, ce qu'il produit comme entités.
🧮
## 🧮 CALCUL & SOURCES :
Formules utilisées, entités sources, méthode de calcul (Riemann, statistics, mean...).
🔗
## 🔗 CHAÎNE DE DÉPENDANCES :
Tableau à 4 colonnes : une ligne par entité produite par ce fichier.
MATÉRIEL
CAPTEUR BRUT
CE FICHIER
AVAL
Device physique ou intégration HA. Si calculé : [calculé]
Entité source exacte utilisée dans source: ou entity_id:
unique_id exact de l'entité produite par ce fichier
Fichier(s) consommateurs + vignette. Ex : P1_UM.yaml → L2C2
⚠️
## ⚠️ IMPORTANT (PIÈGES) :
Comportements contre-intuitifs, dépendances critiques, bugs connus. Ce qui peut casser HA si oublié.
🖥️
## 🖥️ TABLEAU DE BORD (VIGNETTES PRINCIPALES) :
Quelle(s) vignette(s) consomment les entités de ce fichier. Ex : L2C2 Conso Énergie Clim.

7 — Slug tertiaire

Commentaire repère positionné juste au-dessus de chaque bloc d'entité. Doit être l'image exacte du unique_id qui suit - ni plus, ni moins.

Format

# --- unique_id_exact ---
Position : juste au-dessus de chaque bloc d'entité individuel.
Le slug est l'image exacte du unique_id - pas de variation, pas de raccourci.

Cas particulier : Utility_meter

Un slug par entrée de cycle : annuel, mensuel, hebdomadaire, quotidien.
Interdit : un slug groupé pour les 4 cycles.

8 — name & unique_id

Toujours en paire. Même sens, deux formats. Cohérence croisée obligatoire : ils doivent décrire exactement la même chose.

name - format humain

Format : "Préfixe Nom Lisible Période"
Majuscules initiales sur chaque mot.
Préfixe pôle obligatoire en premier mot.
Période ou cycle lisible à la fin si applicable.

unique_id - format machine

Format : prefixe_nom_lisible_periode
Tout en minuscules, séparateurs underscores.
Doit décrire la même chose que name.
Aucune abréviation inventée hors liste officielle.
