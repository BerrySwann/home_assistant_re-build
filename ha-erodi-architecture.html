01 · Config YAML

      
Sensors · Templates · UM
/homeassistant/ → prod HA

      
Claude a un accès direct aux fichiers .yaml sous /config sur le serveur HA : à chaque modification, c'est lui qui récupère le fichier changé et qui le stocke individuellement dans DOCS/01_docs_config_system/config_system_YAML/{pole}/, une fois validé par le créateur. Pour les automations (regroupées dans un seul automations.yaml), l'injection se fait toujours à la main dans l'UI HA ; une fois la modification validée, Claude ne fait que récupérer le bloc changé et le stocke individuellement. Le dashboard, lui, n'est pas un fichier .yaml accessible de la même façon — limitation technique qui oblige le créateur à le récupérer à la main.

configuration.md ne documente que les 6 fichiers YAML à la racine de /config/ (configuration.yaml, camera.yaml, input_button.yaml, groups/, shell_command.yaml, sql.yaml) — pas les dossiers modulaires. sensors/, templates/, utility_meter/, command_line/ n'ont pas de .md parce qu'ils n'en ont pas besoin : les renseignements (description, calcul, dépendances, pièges) sont écrits directement dans les .yaml eux-mêmes, via les headers obligatoires. 1 fonction = 1 fichier, par pôle

          
Chaque fichier YAML ne fait qu'une seule chose : mesurer, compter, calculer, ou afficher. On ne mélange jamais les pôles dans un même fichier. Une prise connectée ne cohabite pas avec un radiateur. L'approche monolithique est interdite.

        

      

    


    
    

      
2 — Numérotation officielle des pièces

      
Index fixe de 1 à 9 pour chaque pièce. Cet index précède le nom dans tous les titres secondaires de chaque fichier YAML, quel que soit le pôle.

      

        
1.ENTREE

        
2.CELLIER

        
3.TOILETTE

        
4.SALON

        
5.CUISINE

        
6.COULOIR

        
7.BUREAU

        
8.SDB

        
9.CHAMBRE

      

      
Exemple : la boite ┌ 4. SALON ┐ dans un fichier P1 signifie "ce bloc appartient au pôle Chauffage, pièce SALON (index 4)". La numérotation garantit l'ordre et l'unicité dans tout le projet.

    


    
    

      
3 — Convention de nommage : Abréviations officielles

      
Toutes les abréviations utilisées dans les noms de fichiers et les unique_id. Organisées par rôle dans la chaine de traitement. Hors de cette liste = interdit.

      


        
        

          
Répertoires — "ou je suis née" — le répertoire détermine la plateforme HA qui charge le fichier

          


            
            
3 piliers principaux · Sensors · Templates · Utility Meter

            
SNSsensors/ — capteur statistique, Riemann, commande shell retournant une valeur. Merge : !include_dir_merge_list

            
UMutility_meter/ — compteur a remise a zero automatique par cycle — consomme _energy et génère des _um. Merge : !include_dir_merge_named

            
TPLtemplates/ — entité calculée par formule Jinja2, aucun hardware direct. Merge : !include_dir_merge_list


            
            

            
Secondaires

            
CMDcommand_line/ — sensor via script bash ; le résultat texte/JSON est interprété par HA comme valeur d'entité

            
IBinput_booleans/ — stockage d'état on/off pour les BV. Chaque IB est appairé a un SW template. Pas utilisé seul.

            
SHshell_command/ - commandes shell déclenchées par HA (boutons, automations). Execution pure, pas de valeur retournée. (pas d'abréviation dans les noms de fichiers)

            
GRP_groups/ — groupes d'entités par constructeur (batteries Hue, IKEA, Sonoff). Ex : GRP_01_batteries_hue.yaml

          

        


        
        

          
Natifs — données brutes exposées directement par le hardware, aucune transformation

          

            
POWER_power — puissance instantanée en W, lue en temps réel via Z2M ou Shelly. Ne s'accumule pas. Sert de source aux calculs AVG et aux totaux de puissance.

            
ENERGIE_energy Z2M — énergie cumulée en kWh, index qui ne fait qu'augmenter. Source directe des Utility Meters. Périmètre : P0 (Nodon pince générale), P1 (prises NOUS chauffage), P2 (prises NOUS/IKEA). ⛔ Ne pas confondre avec la variante PowerCalc ci-dessous.

          

        


        
        

          
Pseudo-natifs — P3 uniquement — PowerCalc estime l'énergie là où le hardware n'expose rien nativement

          

            
ENERGIE_energy PowerCalc (P3) — énergie estimée générée par PowerCalc pour les ampoules Hue (bridge Zigbee, aucun kWh natif). Même suffixe _energy que les natifs Z2M, mais la source est l'état on/off multiplié par un wattage connu — pas une mesure réelle. Exception : relais_lumiere_sdb_sonoff (ZBMINIR2) → 10W fixe. ⛔ PowerCalc interdit sur P0/P1/P2 (monitoring natif Z2M présent).

          

        


        
        

          
Calculs — entités produites par transformation d'une source brute, d'un UM, ou d'un autre sensor

          

            
kWhIntégration numérique W → kWh (méthode Riemann) — utilisé quand le hardware n'expose pas de _energy natif. Cas exceptionnel. Pattern fichier : {P}_kWh_{description}.yaml. Voir la section "Spécial Riemann" ci-dessous.

            
DUTDuration Under Threshold — durée pendant laquelle une valeur (typiquement une température) reste sous un seuil donné. Usage : analyse thermique P1 (confort vs consigne).

            
DIAGDiagnostic cycle en cours (1 seul cycle actif) — snapshot temporaire pour analyser une conso sur une période glissante non clôturée. Fichier de travail, non archivé à terme.

            
AVGMoyenne de puissance en W sur un cycle — calculée depuis _um_kwh_tpl en P3, directement depuis _um en P0/P1/P2. Permet d'évaluer la puissance réelle moyenne consommée.

            
TOTALAgrégat de plusieurs entités du même type sur un périmètre défini — somme de zones, de pôles, etc. Toujours suffixé _AMHQ si le fichier couvre les 4 cycles.

            
HP / HCHeures Pleines / Heures Creuses — sous-entités générées automatiquement par HA quand un Utility Meter est configuré en mode tarif différencié. Source : Linky via MyElectricalData (P0). Suffixes _hp et _hc dans les unique_id.

            
MINI_MAXI_AVGStats min / max / moyenne sur une fenêtre temporelle fixe et glissante (ex: 24h, 7 jours). Distinct de AVG cycle UM : ici la fenêtre est continue et non remise à zéro à minuit. Ex : P0_MINI_MAXI_AVG_Genelec_appart.yaml.

          

        


        
        

          
Cycles

          

            
AMHQAnnuel / Mensuel / Hebdomadaire / Quotidien — les 4 cycles de remise à zéro des Utility Meters. Présent dans le nom de fichier si les 4 cycles sont couverts. Dans les unique_id : forme complète (annuel, mensuel, hebdomadaire, quotidien), jamais l'abréviation.

          

        


        
        

          
Reste

IBInput Boolean — stockage de l'état on/off du BV. Fichier dans input_booleans/. Pattern : {P}_BV_IB_{description}.yaml. Sans IB, le template switch n'a nulle part où persister son état.

4 — Convention de nommage : la chaîne de suffixes

      
Le suffixe du unique_id documente la dernière transformation subie. Chaque étape ajoute sa marque dans le nom.


      

        

          
source brute

          
{slug}_energy

          
Natif HA - Z2M / Hue / Shelly

        

        
→

        

          
Utility Meter

          
{slug}_{cycle}_um

          
Remis à zéro par cycle A/M/H/Q

        

        
→

        

          
Relais kWh (unité + zone)

          
{slug}_{cycle}_um_kwh_tpl

          
Par lampe OU agrégat zone

        

        
→

        

          
Agrégat total

          
{zone}_{cycle}_kwh_tpl

          
Sans _um_ — total appart uniquement

        

      


      

        

          
Règle absolue

          
Tout sensor sorti d'un UM finit par _um. Template kWh (lampe ou zone) : _um_kwh_tpl.

        

        

          
Règle d'agrégation

          
_kwh_tpl (sans _um_) = réservé au total appart entier. Ne jamais l'utiliser à un autre niveau.

        

        

          
P3 — suffixe AVG

          
P3 : AVG calculé depuis _um_kwh_tpl — pas depuis _um directement. Suffixe : _avg_watts_{cycle}.
P0 + P1 + P2 : AVG calculé directement depuis _um — pas de _um_kwh_tpl intermédiaire.

3 — Slug tertiaire

      
Commentaire repère positionné juste au-dessus de chaque bloc d'entité. Doit être l'image exacte du unique_id qui suit - ni plus, ni moins.

      

        

          
Format

          

            # --- unique_id_exact ---

            Position : juste au-dessus de chaque bloc d'entité individuel.

            Le slug est l'image exacte du unique_id - pas de variation, pas de raccourci.
          

        

        

          
Cas particulier : Utility_meter

          

            Un slug par entrée de cycle : annuel, mensuel, hebdomadaire, quotidien.

            Interdit : un slug groupé pour les 4 cycles.
          

        

      

    


    
    

      
4 — name & unique_id

      
Toujours en paire. Même sens, deux formats. Cohérence croisée obligatoire : ils doivent décrire exactement la même chose.

      

        

          
name - format humain

            Majuscules initiales sur chaque mot.

            Préfixe pôle obligatoire en premier mot.

            Période ou cycle lisible à la fin si applicable.
          

        

        

          
unique_id - format machine

          

            Format : prefixe_nom_lisible_periode

            Tout en minuscules, séparateurs underscores.

            Doit décrire la même chose que name.

            Aucune abréviation inventée hors liste officielle.
